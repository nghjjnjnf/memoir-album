# 共享记忆与上下文压缩设计

状态：MVP 已实现  
更新日期：2026-08-30

## 目标

长访谈不能依赖把全部历史对话反复发送给模型，同时各 Agent 又必须认识同一位用户的重要人物、人生事件与已确认事实。因此系统将“事实记忆”“叙事记忆”和“会话摘要”分开管理：压缩只减少模型输入，不删除原始录音、文字、照片、事实或章节版本。

## 三层上下文

1. `LifeContextSnapshot`：所有 Agent 共用的人生骨架，包含主人公、重要人物、人物关系证据、按人生时间排序的重要事件、关键事实、冲突以及整书主题。快照具有版本号与来源指纹，源数据不变时复用，事实或事件变化时生成新版本。
2. 会话工作记忆：当前照片、最近对话、当前事件事实及未解线索。默认保留最近 10 轮，保证局部对话自然连贯。
3. 滚动摘要：仅在预计上下文超过阈值时生成，保存已谈主题、未解线索、用户表达偏好、边界、重要原话及关联事实 ID。摘要不能创造新人物、日期、地点或因果。

章节与整书正文属于 `narrative_derivative_not_fact`。它们可以帮助 Agent 理解主题、人物发展和前后呼应，但不得反向升级为人生事实；人物、时间、地点、关系和事件结果仍以结构化事实与原始证据为准。

## 触发和压缩流程

每次访谈回复、章节生成或章节修订前，协调器估算“共享快照 + 旧摘要 + 尚未压缩的对话 + 当前事实”的 token 数。未达到阈值时直接使用原上下文；达到阈值后，保留当前用户输入和最近对话，将更早内容交给压缩 Agent 生成结构化摘要，再将“共享快照 + 摘要 + 最近对话 + 当前事实”送给业务 Agent。

默认参数：

```env
CONTEXT_COMPRESSION_TRIGGER_TOKENS=6000
CONTEXT_COMPRESSION_TARGET_TOKENS=3500
CONTEXT_RECENT_TURNS=10
LIFE_SNAPSHOT_MAX_PEOPLE=24
LIFE_SNAPSHOT_MAX_EVENTS=30
```

`TRIGGER` 是启动压缩的上界，`TARGET` 是压缩后的目标预算。共享人物、重要事件、当前问题和安全规则属于保护区，即使其本身较长也不会被简单截断。中文 token 使用保守估算，未来切换模型时可替换成供应商 tokenizer，而无需改变存储结构。

## 一致性与可追溯性

- 原始对话只追加、不覆盖；压缩记录保存覆盖至哪一条 turn、压缩前后 token 数和摘要版本。
- 每次模型调用记录使用的共享快照 ID，所有 Agent 在同一次事实状态下看到一致的人物与事件。
- 新事实导致快照来源指纹变化并创建新版本；旧模型运行仍可通过快照 ID 追溯。
- 冲突事实单独进入 `conflicts`，摘要不得替用户裁决。
- 生成正文只能进入叙事记忆，不能进入事实检索集合，避免“模型写过一次便被当真”的循环污染。

## 接口与验收

`GET /api/projects/{project_id}/memory-context` 返回当前共享快照、压缩策略及各访谈会话的压缩状态。自动测试覆盖共享快照注入、阈值触发、压缩版本写入、摘要继续参与访谈以及原始 turns 完整保留。

当前回归结果为 `33 passed`；周桂兰案例共享快照包含 11 个核心人物和 8 个按 1965—2025 排序的重要事件，Demo 预检 `26/26` 通过。
